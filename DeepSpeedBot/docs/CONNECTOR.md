# Подключение и протокол

DeepMove принимает HTTP JSON. **PGN — запись, FEN — позиция, UCI-строка — отдельный ход.** Нативный движок дополнительно говорит UCI через stdin/stdout; HTTP-адаптер переводит уже существующий API без изменений сервера. Официальная схема — [../../docs/BOT_API.md](../../docs/BOT_API.md).

## Пример участника

```sh
python DeepSpeedBot/run.py --url http://127.0.0.1:3000 \
  --game 00000000-0000-0000-0000-000000000000 --side w \
  --mode adaptive --ponder multi --single-core
```

UUID выше — шаблон: взять реальный из ссылки на созданную партию. Токен запрашивается скрытым вводом. Можно передать `DEEPSPEED_BOT_TOKEN` через окружение процесса; не помещать его в аргументы, URL, PGN, Git или телеметрию. Ключ относится только к одному месту одной партии. `--side` должен совпадать; ready-ответ проверяется. Удалённое соединение — HTTPS с системной проверкой сертификата; незашифрованный HTTP разрешён только loopback.

Создание партии 300/3 выполняется в UI или существующим cookie API:

```json
{
  "format": "custom", "initialSeconds": 300,
  "incrementSeconds": 0, "botMoveSeconds": 3,
  "startDelaySeconds": 8, "side": "w", "kind": "bot",
  "opponentKind": "bot", "engineName": "DeepSpeedBot"
}
```

Предел 400 **полных** ходов = 800 полуходов не реализован сервером. Не путать его с ограничением текущего анализа архива в 400 полуходов. Коннектор поддерживает 1500 полуходов и не объявляет локальные ничьи от имени сервера.

## Последовательность и безопасность

1. `GET /api/arena/games/ID` без секретов; проверить bot seat, статус, историю и часы.
2. Если waiting и место не ready — `POST .../ready {}` с `Authorization: Bearer KEY`. После готовности обоих ждать серверный countdown, не запускать часы самому.
3. В чужую очередь загрузить полную историю в постоянный C++-процесс и запустить `dmponder`. HTTP-опрос раз в 200 мс продолжает работать независимо от поискового worker.
4. В свою очередь прервать старый pondering, передать актуальную историю, учесть наблюдаемое время противника, вычислить дедлайн с RTT/запасом. При hit взять готовый ответ, иначе короткий поиск.
5. Проверить результат по **официальному** `state.legalMoves` и отправить `POST .../move {"move":"e2e4","expectedPly":N}`.
6. Новая история принимается только из подтверждения сервера. Если ответ потерян, 409 или временная ошибка — сначала GET, затем решить по актуальной очереди; слепого повтора POST нет. После подтверждённого собственного хода сразу снова начинается pondering.
7. Finished останавливает worker и записывает итог. Перезапуск клиента восстанавливает историю и часы с сервера; готовность уже идущей игры не отправляется.

HTTP-клиент использует keep-alive `http.client`. Redirect не выполняется, особенно с bearer-ключом. Ограничен объём ответа, запрещены userinfo/query/path в origin и переносы строк в протокольных командах. 401/403/404/422 завершают клиента; 429 соблюдает Retry-After, 409 и 5xx вызывают повторное чтение. Сетевое восстановление не останавливает игровые часы. Допустимый polling 0.2–5 с; запуск нескольких клиентов для одного места не предусмотрен.

Стандартный формат арены по-прежнему 600/3, custom из ТЗ — 300/3. Передача собственных timestamp, позиции или остатка времени на сервер не используется. Никакого исполнения кода на Next.js-сервере, обхода квот или изучения чужого процесса.

## Нативный UCI

```text
uci
isready
ucinewgame
setoption name Hash value 32
setoption name Mode value balanced
position startpos moves e2e4 e7e5
go movetime 70
# ... info depth ... score cp ... nodes ... time ... pv ...
# ... info string dmresult {"move":"...",...}
# bestmove ...
quit
```

Поддерживаются `position startpos [moves ...]`, `position fen SIX_FIELDS [moves ...]`, `go movetime|depth|nodes`, `wtime/btime`, `winc/binc`, `go infinite`, `go ponder`, `ponderhit`, `stop`, `quit`. Один search thread; `Threads>1` отклоняется. `Ponder` option объявлена для совместимости; фактический запуск контролируется `go ponder`/адаптером. Варианты Chess960 и `searchmoves` не поддерживаются. Для терминальной позиции `bestmove 0000`. Входная строка до 64 КиБ, история до 1500 полуходов. FEN сам по себе не содержит повторений: для реальной партии используйте startpos с полной историей.

Обычный `go ponder` имеет стандартный смысл: позиция уже включает прогнозируемый ход; `ponderhit` разрешает завершить поиск в своём времени. Для нескольких прогнозов адаптер использует расширение:

| Команда | Действие |
| --- | --- |
| `dmponder single` | Предварительный расчёт ответа на один наиболее вероятный ход из текущей позиции соперника |
| `dmponder multi` | Несколько ответов с равными slices |
| `dmponder adaptive` | Несколько ответов с весами вероятности/сложности/числа посещений |
| `go wtime 300000 hardtime 2700` | Адаптивное распределение внутри уже безопасного hardtime, мс |
| `dmconfig complexity 0` | Изменить ограниченный параметр, см. config/default.conf |
| `dmobserve MS CHECK CAPTURE COMPLEXITY PHASE REMAINING_MS` | Официальное наблюдение о последнем ходе соперника; phase=0/1/2 |
| `dmfeatures` | Нормализованные признаки текущей позиции |
| `dmmodel` | Статистика наблюдения и корреляция |
| `dmlegal`, `perft N`, `d` | Легальные UCI, perft до глубины 7, FEN для проверки |

Передав следующую `position`, адаптер автоматически останавливает `dmponder`. TT и подготовленные ответы остаются в процессе; новый `go` проверяет hit по истории и позиции. `isready` отвечает без остановки поиска; после `position` он служит барьером, потому что обработчик position уже дождался отмены worker.

Для собственного клиента можно использовать `adapter.engine.Engine` как контекстный менеджер, `position(history)`, `think(remaining_ms,hard_ms,side=...)`, `ponder(strategy)`. `adapter.arena.play` — полный рабочий пример правильного HTTP-цикла. C++-ядро также можно подключать к обычному локальному UCI GUI без Python.

## Телеметрия

Клиент пишет JSONL в stdout и опционально `--log PATH`. Это отдельный поток от UCI stdout дочернего процесса. Секретов и HTTP-тел нет. На ход: UCI, score_cp со стороны хода, глубина, nodes/qnodes, NPS, TT hits, cutoffs, reductions, search elapsed_ms, hard_budget_ms, ponder hit/opportunity, подготовленные ponder_ms/nodes. На окончание pondering: общие узлы, elapsed_ms, ветки и cycles. На партию: результат/причина, длительность, расход серверных часов, число ходов и взятий, hit rate, модель соперника.

`elapsed_ms` поиска не включает весь HTTP/polling/IPC. `ponder_ms` — длительность работы веток по настенным монотонным часам, не отдельный CPU-счётчик. На hit nodes=0 и NPS=0 относятся к новому ходу; глубина относится к ранее рассчитанному ответу. Не складывайте ponder-узлы в CPU узлы собственного хода. В матчевых отчётах useful ponder nodes — сумма узлов веток, давших hit; это верхняя прокси полезности, а не точное число узлов, прочитанных из TT.

Ограничения текущего API — 20 созданий партий/час на аккаунт, 5 активных и публичное чтение по HTTP. Поэтому большая воспроизводимая серия проводится локальным арбитром, а совместимость проверяется полными матчами настоящего API в отдельной SQLite. Скрипты не обходят ограничения рабочего сервера.
