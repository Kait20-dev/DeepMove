# Архитектура

DeepMove состоит из серверной арены, независимых коннекторов участников и
статического сайта проекта. Общий язык между движком и сервером — HTTP и JSON.

## Поток одного хода

```text
Алгоритм участника                   Сервер арены
       │                                  │
       ├── GET состояние ────────────────►│
       │◄── FEN, история, deadline ───────┤
       │                                  │
       ├── свой поиск с бюджетом           │
       ├── POST UCI + expectedPly ────────►│
       │                         Bearer + принадлежность
       │                         часы + очередь + правила
       │                         SQLite-транзакция
       │◄── новое состояние ──────────────┤
       │                                  └── зрительский GET
```

Сервер не запускает пользовательский код, не принимает URL движка и не
доверяет присланным оценкам, часам или результату. Участник не может
подменить позицию: на сервер уходит только ход и ожидаемый полуход.

## Правила и часы

Авторитетная шахматная позиция хранится на сервере. Правила проверяет
`chess.js`. `expectedPly` защищает от повторного применения хода и запросов
для устаревшего состояния. Ходы сериализуются SQLite-транзакциями
`BEGIN IMMEDIATE`; одновременно принять два хода для одного полухода нельзя.

Старт задаётся серверной меткой `startsAt`. Повторный ready не сдвигает её.
Часы активной стороны расходуются от `turnStartedAt`; учитывается минимум
общего остатка и лимита отдельного хода. Перезапуск сервера и отсутствие
зрителей не дают дополнительного времени.

Для первого позднего легального запроса сохраняется фактическое опоздание
от серверного дедлайна. Если запроса не было, сервер не придумывает его
длительность или причину зависания. Подробности — [HTTP API](BOT_API.md).

## Хранение и результаты

SQLite работает в WAL-режиме. База и её служебные файлы лежат на постоянном
диске. В ней сохраняются пользователи, сессии, команды, карточки ботов,
состояния матчей, серии и очки.

У каждого зарегистрированного бота постоянный ID. Серия фиксирует состав
и команды при принятии приглашения. После четырёх результатов очки
попадают в оба кубка в одной транзакции. Уникальность записей не даёт
начислить их повторно; последующий переход не переносит старые очки.

Лобби получает короткие карточки последних 50 партий, а не весь PGN и
разбор каждого архива. Таблицы кубков используют записи результатов всех
завершённых серий. Публичные ответы не содержат приватных хешей.

## Ключи и сессии

- Пароли хешируются `scrypt` с индивидуальной солью.
- Сессии живут в HttpOnly / SameSite=Strict cookie; в БД хранится хеш токена.
- Изменяющие браузерные запросы проверяют Origin и текущую сессию.
- Ключ отдельной партии ограничен одним игровым местом.
- Ключ серии выдаёт только соответствующие игровые ключи её участника.
- Перевыпуск отзывает предыдущий ключ. Секреты не записываются в PGN.
- Размер JSON и частота запросов ограничены сервером.

## Stockfish после игры

Анализ работает локально через UCI, не через внешний API. Движок —
Stockfish 19 Lite из npm-пакета `stockfish`. Анализ ограничен глубиной 12 /
30 тысячами узлов на позицию; отчёт сохраняется в партии. Подсказки живой
игры не выдаются. Метки качества — открытые эвристики DeepMove, зависящие
от глубины анализа, а не гарантированные оценки или алгоритмы Chess.com.

## Статический сайт и документация

`npm run build:pages` создаёт `out/` из `site/` и Markdown-источников.
Для HTML используется Marked. Документация получает боковое меню,
оглавление, поиск и ссылки на исходные файлы. Локальные Markdown-ссылки
преобразуются в адреса страниц; ссылки на код ведут в GitHub.

Сайт использует относительные пути и работает в подпапке `/DeepMove/`.
В сборку не входят SQLite, серверные маршруты, ключи, логи матчей или
`node_modules`. Фоновая шахматная сцена использует ту же проверенную последовательность, что
и основной сайт, и выполняется в браузере независимо от API арены. Это
декоративная анимация, а не трансляция реальной партии.

## Границы текущей версии

Сервер рассчитан на один постоянный Node-процесс. Несколько независимых
реплик потребуют общего координатора времени и очереди анализа.
Обновления идут через HTTP polling, а не WebSocket.

Удалённый протокол не доказывает авторство движка и не запрещает участнику
самостоятельно запустить внешние подсказки. Для официального турнира нужны
проверка исходников и изолированный запуск утверждённых сборок.
